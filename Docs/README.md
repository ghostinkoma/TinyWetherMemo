# ThunderSense — AS3935 雷センサ I2C ブリッジ (CH32V003)

秋月 **AE-AS3935**（AMS AS3935 Franklin Lightning Sensor）を **CH32V003J4M6 (SOP-8)** で受け、
上位ホスト（**ESP32** 等）へ **I2C スレーブ**として「雷イベント列」を供給する中継デバイス。

- 雷センサ側 : **ソフトウェア I2C**（CH32V003 がマスタ）
- 上位バス側 : **ハードウェア I2C**（CH32V003 がスレーブ／他の温湿度センサ等と同居）
- 時刻 : CH32V003 の **SysTick ソフト時計**を、ESP32 の **NTP 時刻**と対応付けて **絶対タイムスタンプ**化

---

## 1. なぜブリッジするのか（設計根拠）

AS3935 の IRQ はバスをアービトレーションしない（ただのスレーブ＋専用割込線）。
それでもブリッジを挟むのは、次の実在利点のため：

1. **CH32V003 の I2C ペリフェラルは 1 個だけ**。それを上位バスの**スレーブ**に使う以上、
   AS3935 と話す**マスタ用の 2 本目の I2C（＝SW-I2C）が必然**。
2. **AS3935 の I2C は癖が強い**（ハングしやすい）。上位バスに直結すると温湿度センサまで巻き添え。
   ローカル SW-I2C（短配線）に**隔離**する。
3. **EMI 隔離**。高感度アンテナの近くを上位バスの往来が通ると false *disturber* を誘発。閉域化で低減。
4. **上位 MCU の FW 単純化**。非同期 IRQ 処理を CH32 が肩代わりし、ESP32 は「N 秒ごとに読むだけ」。

> ⚠️ 用語補正：本設計で希少なのは **GPIO ピン（J4M6 で 5 本）** であって内蔵ペリフェラルではない。
> SysTick を時計＋µs 遅延に使い、TIM を温存する方針（TIM1/TIM2 は結果的に全空き）。

## 2. 役割分担（最重要）

| 主体 | 動作 | 周期 |
|---|---|---|
| **CH32V003** | AS3935 の IRQ を**即時・イベント駆動**で捕捉→ビン化して保持 | イベント毎（リアルタイム） |
| **ESP32** | CH32V003 を**ポーリング**してビン列をまとめて回収 | N 秒（例 1 秒） |

例）1 秒間に 0.2 秒間隔で 5 回発生 → CH32 が 5 ビンを保持 → 次ポーリングで **5 件まとめて** ESP32 へ。

## 3. スケジューリング哲学：雷ファースト／ESP32 ベストエフォート

- **既定は Busy を返す**。空いている（キャプチャ中でない）ときだけデータを返す。
- Busy の実体は **AS3935 への SW-I2C ビットバング中(~1ms)** の保護。1 イベント占有 ≒ 3ms。
  - 5 件/秒でも Busy は約 1.5%／秒 → **ESP32 可用性 98% 超**。
- **読むのは shipping バッファ、雷が書くのは active バッファ（物理的に別）**。
  → 「読ませること」自体は雷を 1 件も失わない。

詳細は [SPEC.md](SPEC.md) の「割込優先度」「状態機械」を参照。

## 4. ハードウェア

### 4.1 ピン割当（CH32V003J4M6 / SOP-8）※データシート準拠

| 物理Pin | ポート | 割当 | 主な代替機能 |
|---|---|---|---|
| 1 | **PA1** | **SW-I2C SCL → AS3935**（マスタ） | ADC A1 / T1CH2 / OSC（※PD6 等がボンディング共有） |
| 2 | VSS | GND | — |
| 3 | **PA2** | **SW-I2C SDA → AS3935**（マスタ） | ADC A0 / T1CH2N / OSC |
| 4 | VDD | 3.3V | — |
| 5 | **PC1** | **HW-I2C1 SDA（上位バス・スレーブ）** | I2C1 既定 SDA / NSS |
| 6 | **PC2** | **HW-I2C1 SCL（上位バス・スレーブ）** | I2C1 既定 SCL / URTS |
| 7 | **PC4** | **AS3935 IRQ（EXTI）／T1CH4（IC・LCO校正兼用）** | ADC A2 / MCO |
| 8 | **PD1** | **SWIO（書込専用）** | SWDIO / T1CH3N（PD4/PD5 共有） |

**確定した重要事実（データシート／公式ピン表）**
- **PC1/PC2 は SOP-8 に存在し、既定 I2C1（remap 不要）**。→ 上位バスは PC1(SDA)/PC2(SCL)。
- **J4M6 は複数ダイポートを 1 物理ピンにボンディング**（例 Pin1=PA1 に PD6 等が同居）。
  → **1 ピンにつき使うポート名を 1 つに統一し、同居ポートは未設定**にすること。
- **PA1/PA2 を使うため外部クリスタル不可** → **内蔵 HSI 運用**（時計ドリフト ±1% は ESP32 再同期で吸収、[SPEC.md](SPEC.md) §6）。
- **PD1=SWIO は書込専用で温存**。運用中 GPIO 転用は再書込困難＋ブリック риск のため不可。
- ⚠️ **予備 GPIO はゼロ**（6 GPIO 全使用）。→ **AS3935 のハード電源断（power-cycle）用ピンが無い**。
  ハング回復は SW バス回復＋IWDG に限られる（[SPEC.md](SPEC.md) §14）。ハード電源断が必須なら **TSSOP20(F4P6) 検討**。

**データシート参照元**
- 公式 CH32V003 データシート（秋月ミラー）: https://akizukidenshi.com/goodsaffix/CH32V003.pdf
- ピン表クロスチェック: https://github.com/ch32-riscv-ug/CH32V003 ／ EEVblog「CH32V003-J4 (SOP8) pins」
- ⚠️ 物理ピン番号は**実機・正式データシート現物で最終確認**（ボンディング表記に版差あり）。

### 4.2 電源・レベル
- CH32V003 = 3.3V。AS3935 モジュールのロジックも 3.3V 側に合わせる。
- SW-I2C はプルアップ必須（AS3935 モジュール側/基板側どちらかで）。

## 5. 主要データ構造（概要）

- **イベントビン（12B 固定）**：type / distance / energy(20bit) / **絶対 timestamp(epoch4+ms2)** / seq
- **バンドル**：`[status][length][gen][bins[32]][crc16]`（固定 389B）
  - **トリプルバッファ 3 段**（fill 充填 / serve 回収 / clear 背景ゼロ消去）
  - **CRC16 一括**（ブロック規模的に CRC8 は弱い）／未使用ビンは 0x00 埋め／クリアは CRC 先消去
- **命令バッファ**：ESP32 命令を割込で受け、実行はメインループ（**制御経路とデータ経路を分離**）
- **健康度**：Vrefint→VDD(電源)監視（CH32V003 に校正済ダイ温度は無いので目安）
- **フラッシュ校正**：LCO 校正値(TUN_CAP)を option-byte に保存→次回高速起動

詳細は [SPEC.md](SPEC.md) と [I2C_REFERENCE.md](I2C_REFERENCE.md)。

## 6. ロス経路と保全

| 経路 | 対策 |
|---|---|
| キャプチャ中の命令 | 既定 Busy＋命令バッファで取りこぼさない |
| クリア中の雷 | クリアは**割込可能**（割禁しない）＋ shipping/active 分離で非破壊 |
| 読取中の雷 | 別バッファなので影響なし |
| 荒天オーバフロー | **エネルギー上位32保持**（弱い雷を置換）＋ **lost_count**、`lightning_total` 等**単調カウンタで総数保全** |
| 通信エラー | **非破壊 read ＋ (gen,crc) 指定クリア**（ESP32 が検証成功時のみ削除） |
